# 已驗證視窗的排列與色盤來源

2026-09-09：目前室內視窗的兩個背景層，現在能只用 MAP001.TWN 的圖塊、排列及色盤產生。
每層 280 個可見排列項目（20×14）都與存檔中的 VDP2 pattern word 完全一致，
兩張 320×224 RGBA 圖片的 PNG SHA256 也與先前記憶體版本相同。

**攝影機與顯示條件仍是已記錄的參照情境，尚未從原作事件／鏡頭規則推導。**
此成果是背景資料還原，不是完整場景載入、碰撞或可玩切片。

## 第二段資料的用途

MAP001.TWN `0x26C1C` 的 mode-5 區塊解出 65,536 bytes。
目前驗證的解讀為兩層各 128×128 個 big-endian u16 緊湊排列項目：

- layer 0 從解碼資料 `0x0000` 開始；layer 1 從 `0x8000` 開始。
- 每列 256 bytes，每項 2 bytes；目前視窗涵蓋 X=34..53、Y=96..109。
- 低 10 位為圖塊索引，索引乘 8 加 `0x2000` 轉成 VDP2 32-byte 單位圖塊號。
- 高位保留 special-priority 與水平／垂直翻轉；未驗證的其他旗標拒絕。

這個映射已對目前區域逐項核對，包含翻轉圖塊；沒有把其他位置也宣稱為已驗收。
完整排列頁含有與目前周圍不同的資料，部分項目能對上其他來源座標，
與分批更新／循環排列緩衝的解釋相符。但更新函式未追蹤，不能把推論當成動態執行證明。
驗證只比較真正可見的 560 項，不用未顯示的記憶體內容否定已符合的來源資料。

## 色盤來源

第四段 payload 的第二組 256 色色盤，起點為原始檔 `0x2C420`。
色碼 1..255 的 510 bytes 與參照 CRAM 完全一致。
色碼 0 在來源是 `41A9`、參照為 `0000`；本次兩層均啟用索引 0 透明，
因此差異不影響輸出。測試另外改變第 0 色的 RGB，確認整張 RGBA 圖完全不變。
沒有將此規則套用到其他尚未核對的場景或不透明圖層。

## 產物與驗證方式

新增 `tools/decode_source_scene.py`：

- `source_data` 解壓來源圖塊與排列，讀取來源色盤。
- `render_view` 僅接受上述資料與鏡頭座標，不讀取存檔或 RAM。
- `run` 才讀取固定存檔作交叉驗證，檢查 560 個 pattern word 與兩張 PNG。

鏡頭常數為 X=544、Y=1536，來自上一輪的參照暫存器；目前只驗收這個視窗。
不實作角色、NBG3、視窗特效、優先權合成、動畫或遊戲事件。

執行 `tools/run.ps1 -Action test` 會產生：

- `reports/source-scene/nbg0-viewport.png`、`nbg1-viewport.png`：來源資料生成的視窗。
- `reports/source-scene.json`：來源偏移、每項排列的來源座標／解碼偏移、圖塊 ID、參照位址及限制。
- `reports/source-background/layout.bin`：第二段解碼資料；早期的 `block2-unassigned.bin` 不再是目前輸出名稱。

本輪新增 5 項測試，合計 38 項 Python 測試與既有 Godot 14 項契約、9 項驗證台檢查通過。
包括排列旗標／翻轉、列步幅、獨立產圖、透明色差異、不支援參數拒絕及完整視窗回歸。
程式、測試與雜湊摘要納入 Git，遊戲像素與解碼資料保留本地。

下一個關卡是場景入口、鏡頭／載入流程與碰撞資料，讓引擎能依遊戲狀態選擇及載入場景。
Stage B 尚未整體通過，也未新增模擬器遊玩或完整畫面驗收。
