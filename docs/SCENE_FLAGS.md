# MAP001 第三段：旗標表重建

2026-09-09：已追到原程式讀取者，將第三段展開為 256×256 byte 表。
來源解碼結果與鎖定 Ymir 存檔的 Work RAM Low `0x10000:0x20000` 全部一致，
共 65,536 bytes、0 差異。這確認資料展開方式；旗標對移動、事件、碰撞的作用尚未確認。

## 原程式證據

TWN.BIN 的執行基址為 `0x06090000`，以下為檔案偏移。

- `0x1E62` 從常數池 `0x1F6C` 載入 `0x260F4000`，呼叫 `0x060AE34E`。
  先前只搜尋 `0x060F4000`，漏掉這個位址表示法。來源區塊與 High RAM 的完整比對仍由既有探測器驗證。
- `0x1E0B4` 起的區塊分派器讀取八位元組標頭；tag 3 分支 `0x1E124`
  將 `0x260F4000` 作為搬移目的地，再於 `0x1E12C` 呼叫同一個展開例程。
  搬移函式內部尚未在本輪驗證，不把靜態呼叫路徑當成新的動態執行紀錄。
- 展開例程 `0x1E34E` 將 `0x20210000` 起 65,536 bytes 初始化為 `0x03`，
  順序處理八組 count。每組 count 是大端序 u16，每筆資料占四 bytes。
- OR helper `0x1E40C` 與 AND helper `0x1E4A6` 讀取 x、y、width、height，
  以 `y*256+x` 算起點，每列加 256，每格依指定遮罩進行位元運算。
- `0x1E51A` 只消耗 count×4 bytes；不寫入旗標表。

| 組別（從 0 起） | MAP001 筆數 | 此讀取者執行方式 |
|---|---:|---|
| 0 | 433 | OR 0x80 |
| 1 | 0 | OR 0x40 |
| 2 | 20 | OR 0x20 |
| 3 | 0 | OR 0x10 |
| 4 | 1 | 讀過記錄，不寫入；呼叫時傳入 0x08 |
| 5 | 0 | 讀過記錄，不寫入；呼叫時傳入 0x04 |
| 6 | 477 | AND 0xFD，清除 bit 1 |
| 7 | 0 | AND 0xFE，清除 bit 0 |

因此先前「零 count 或對齊字」的歧義在此讀取者已解除：是八組 count。
width 或 height 為零時沒有寫入；第 6 組不少這類記錄並非格式錯誤。
第 4、5 組被此例程跳過，不能據此宣稱整個遊戲都不使用它們。

## 重現與驗證

`tools/decode_scene_flags.py` 僅用來源檔建立旗標表，存檔只用於結果比對。
它驗證來源雜湊、完整讀取例程／常數範圍的雜湊、八組數量、資料邊界及寫入範圍。
不自行裁切越界矩形；列尾線性跨列保留原程式行為，超出 64 KiB 的寫入拒絕。

輸出 SHA256：`78863dedbf02a07158821486a059af56f31a0b18d11a9eee6a7986dd10943e5b`。
完整結果在本地 `reports/scene-flags.json`、`reports/scene-flags/flags.bin`；
提交摘要為 `docs/scene-flags-validation.json`，不提交來源資料或重建表。

六項新增測試涵蓋操作順序、零尺寸、跳過群組、線性跨列、結構／越界拒絕、
程式突變拒絕及完整來源與存檔比對。全套測試目前 Python 48 項，Godot 14+9 項通過。

反組譯使用既有唯讀 Ghidra 專案與 `DumpSceneRanges.java`，
主要範圍 `0x1E34E:0x1E52C`、`0x1E55E:0x1E564`，
分派／呼叫範圍 `0x1E0B4:0x1E19E`、`0x1E62:0x1E6A`；本地輸出留在 reports。
